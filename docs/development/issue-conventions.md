# Issue Conventions

本プロジェクトの作業・不具合・改善案の記載規則。Issueは「何を、なぜ行い、どこまでできれば完了か」を記録する。

## 基本方針

- 原則として作業前にIssueを作成し、関連するPRへ番号を記載する。
- 1件のIssueは、完了を判断できる1つの目的に絞る。大きい機能は小さい作業へ分割し、親Issueからリンクする。
- 本文は日本語を基本とし、コード・API名は実装の表記に合わせる。
- MVPの機能に関係する場合はF01〜F14のIDを記載する。文書・基盤作業は無理にIDを割り当てない。
- 個人情報、写真、トークン、秘密のキーは本文・画像・ログへ貼らない。再現データは架空の情報を使う。

## タイトル

既存の[Git規約](./git-conventions.md)と同じtypeを使う。

```text
<type>: <作業または解決する問題>
```

| Type | 用途 | 例 |
| --- | --- | --- |
| feat | 新機能 | feat: 履歴書の保存APIを実装する |
| fix | 不具合 | fix: ログアウト後に写真が残る問題を修正する |
| docs | 文書 | docs: Issueの記載規則を定義する |
| test | テスト | test: 別利用者の書類取得を拒否するケースを追加する |
| refactor | 動作を維持した整理 | refactor: 書類入力検証を共通化する |
| ci | CI/CD | ci: 型チェックとビルドを自動実行する |
| chore | その他 | chore: 開発依存を更新する |

「修正」「対応」だけで終わらせず、対象と結果を書く。typeの強制検査は現時点では未導入。

## 本文テンプレート：機能・改善・文書

```markdown
## 背景・目的
困っていること、今回解決する理由。

## 作業範囲
- 実施する内容
- 対象外（必要な場合）

## 完了条件
- [ ] 操作や成果物で確認できる条件

## 確認方法
確認する操作、テスト、文書や画面。

## 関連
MVPのID、関連Issue、仕様・設計へのリンク。なければ「なし」。
```

「実装する」だけでなく「本人の書類を再取得でき、別利用者の取得を拒否する」のように結果を書く。見積もりは必要な作業だけ学習・実装を分けて記録し、確定値として扱わない。

## 本文テンプレート：不具合

```markdown
## 問題
何が困るか。

## 再現手順
1. 架空データで行う操作
2. 問題が発生する操作

## 期待する結果
本来の動作。

## 実際の結果
発生した動作。必要なら秘匿情報を除いたログ・画像。

## 環境
ブラウザ、OS、対象コミット、ローカル／公開環境。

## 完了条件・確認方法
- [ ] 再現手順で問題が解消し、関連する動作も確認できる

## 関連
仕様・MVPのID・関連Issue。
```

## ラベル・優先度・終了

- 作成済みのラベルを確認して使う。推奨候補は `bug`、`enhancement`、`documentation`。追加作成は必要な場合だけ行う。
- 優先度は本文に「必須／推奨／後回し」と理由を書く。ラベルがなくても作業を進められる。
- 必須はMVP成立に必要、推奨は改善、後回しは初期版対象外。優先度は実装順序と同一ではなく、依存関係も確認する。
- 担当者・Milestoneは実際に設定できるものだけ使用する。
- 完了条件を満たした時点で閉じる。未完了部分は残すか別Issueへ分離し、理由を記録する。
- 重複・不採用で閉じる場合も、関連先と理由を記録する。

記載規則のためだけのGitHub Actionsは初期版では導入しない。コピー用テンプレートで運用し、Issue Formsの導入は別作業とする。
