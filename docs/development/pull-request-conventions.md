# Pull Request Conventions

GitHubではマージリクエストに相当するものをPull Request（PR）と呼ぶ。変更理由・差分・検証結果を記録し、mainへ取り込む前に確認する。

## 作成前の作業

1. 関連Issueと完了条件を確認する。
2. 最新mainから作業ブランチを作る。
3. 変更を実装し、差分と必要な検証を確認する。
4. PRを作り、個人開発でもセルフレビューする。

ブランチ名は `<type>/<kebab-caseの短い目的>`。例：`docs/add-issue-conventions`、`feat/add-resume-api`。mainの保護を解除して直接pushしない。

## タイトル

```text
<type>: <変更によってできるようになること>
```

typeは[Git規約](./git-conventions.md)に合わせる。例：`feat: add resume save API`、`docs: define development conventions`。本文は日本語を基本とし、タイトルの説明は日本語・英語のどちらも許可する。

Squash mergeではPRタイトルがコミットタイトルに使われる設定のため、取り込み前にtypeと変更内容を確認する。1つのPRには、1つの目的に必要な変更をまとめる。

## 本文テンプレート

```markdown
## 目的・変更後の動作
何が問題で、今回どのように変わるか。

## 主な変更
- レビューで見るべき変更と、その理由

## 検証
- 実行したコマンド／操作と結果
- 未確認事項・実行できなかった理由（ある場合）

## 関連Issue
Refs #番号
```

画面変更は架空データの画像、不具合修正は再現条件と修正後の結果を添える。API・DBの変更は互換性やマイグレーションの影響も書く。該当しない項目は増やさない。

- 関連するだけの場合や一部対応の場合：`Refs #1`。
- Issue全体の完了条件を満たす場合：本文に `Closes #1`。
- `Closes`による自動終了は、PRをデフォルトブランチへマージした場合の運用とする。未完了のIssueを閉じる目的で使わない。

## レビュー・取り込み

- 未完成の変更はDraft PRとして開く。検証後にレビュー可能な状態へ変更する。
- 差分に無関係な整形、大量のリネーム、秘密値、生成された個人データが混じっていないか確認する。
- MVPの完了条件と、変更に関係するLint・型チェック・Build・重要テストを確認する。CI未整備の段階は手動で確認した内容を記録する。
- 文書変更は、記載内容・リンク先・表記の整合性を確認する。不要なアプリテストは行わない。
- コメントへの対応と必須チェックの成功を確認して、Squash mergeする。必須CIは導入後に実際のチェック名を登録する。
- PRの承認要件を新たに増やさず、現在の個人開発向け設定に従う。
- 取り込み後はmainで反映を確認し、作業ブランチを削除する。
