# 履歴書・職務経歴書作成Webアプリ：MVP仕様

更新日：2026-10-08  
対象リポジトリ：https://github.com/roddhie/ResumeForWebDevelopper  
文書の状態：初期版の仕様。機能の実装完了を示すものではない。

## 1. 目的

Web系エンジニアが、WordやExcelの書式調整に手間をかけず、項目入力から履歴書・職務経歴書を作成し、顔写真付きの履歴書と職務経歴書をPDFとして保存できるようにする。

初期版では、書類の入力・保存・再編集・PDF出力までの利用経路を成立させる。自作APIによる認証検証、入力検証、認可、DB操作も実装対象とする。

## 2. 対象利用者・解決する課題

対象利用者は、転職・応募に向けて履歴書・職務経歴書を作成したいWeb系エンジニア。

- 文書作成ソフトの書式調整に時間がかかる。
- 担当プロジェクトや使用技術を、項目ごとに整理して入力したい。
- 保存した内容を再編集し、提出用PDFを作成したい。
- 顔写真を保存し、別端末でも同じアカウントで利用したい。

## 3. 中心的な利用の流れ

1. Googleアカウントでログインする。
2. 履歴書・職務経歴書を入力し、履歴書に使用する顔写真を選択する。
3. 書類と写真を保存する。保存結果と未保存状態を確認できる。
4. 再ログイン後、または別端末から、保存済みの書類と写真を取得して編集する。
5. プレビューで確認し、ブラウザ印刷からPDFとして保存する。
6. 不要な書類と対応する写真を削除する。

## 4. 必須機能と受け入れ条件

受け入れ条件は、実装完了を判断するために確認する動作を表す。

| ID | 機能 | 初期版の範囲・受け入れ条件 |
|---|---|---|
| F01 | 履歴書入力 | 基本情報、学歴・職歴、資格、志望動機を入力・編集でき、保存・取得した内容が保持される |
| F02 | 職務経歴書入力 | 職務要約、スキル、自己PRを入力・編集でき、保存・取得した内容が保持される |
| F03 | プロジェクト管理 | 期間・担当業務・技術・成果を持つプロジェクトを複数追加・編集・削除でき、保存後も内容が保持される |
| F04 | 入力検証 | 必須項目、形式、長さ、日付関係を画面とAPIで検証する。不正な入力は保存せず、修正対象と理由が分かるエラーを表示する |
| F05 | プレビュー | 各書類の固定テンプレート1種類で入力内容を表示する。履歴書に選択した写真が反映される |
| F06 | PDF保存 | ブラウザ印刷で両書類をPDF保存できる。日本語、長文、複数ページ、写真を含む内容が欠落せず、操作用UIが印刷されない |
| F07 | 顔写真の操作 | JPEG・PNGを選択できる。形式・容量を検証し、比率を保持してリサイズ・表示する。差し替え・削除ができ、不正なファイルを拒否する |
| F08 | 認証 | Supabase Authを使用し、Googleアカウントでログイン・ログアウトできる。認証失敗を通知し、ログアウト時は表示中の個人データをクリアする |
| F09 | 書類CRUD・DB | 本人の履歴書1件・職務経歴書1件を、自作API経由で作成・取得・更新・削除できる。再読み込み・再ログイン後も取得できる |
| F10 | 認可 | APIで認証と所有者を検証する。未認証・別利用者による書類と写真の取得・変更・削除を拒否し、存在や内容を不用意に漏らさない |
| F11 | 写真のクラウド保存・復元 | Supabase Storageの非公開領域に写真を保存し、同じアカウントで別端末から取得できる。DBで所有者・履歴書との対応を管理し、保存失敗を通知する |
| F12 | 書類・写真の削除 | 本人が書類と対応写真を削除できる。履歴書削除時は関連写真も削除する。途中失敗を成功として扱わず、再試行できる |
| F13 | 基本アクセシビリティ・モバイル | 入力欄にラベルがあり、キーボードで主要操作ができる。エラーが分かり、小さい画面でも入力・編集できる |
| F14 | 架空サンプル | 架空のデータを読み込み、入力・プレビュー・PDFを試せる。既存の入力を上書きする場合は確認し、読み込みだけでサーバー保存しない |

### 入力・写真の具体的な制限

入力項目の必須・任意、文字数上限、日付の許容範囲、写真の容量・寸法の上限は、項目設計と写真処理の試作で確定する。未確定値を実装済み仕様として記載しない。確定時に本節を更新し、画面・API・Storageの設定で整合させる。

## 5. データ保存・アクセス制御

### 書類データ

- 文字データはHonoの自作HTTP APIを経由し、Supabase PostgreSQLに保存する。
- APIで認証情報を検証し、利用者IDを確定する。リクエスト本文の所有者IDだけを信用しない。
- APIで入力検証と所有者確認を行い、DB側でもRLS（行単位のアクセス制限）を適用する。
- 通常の書類CRUDで管理者権限を使用してRLSを迂回しない。
- 書類IDを持つ設計とし、初期版では利用者ごとに各書類1件へ制限する。

### 写真

- 写真の永続保存先はSupabase Storageの非公開領域とする。IndexedDBによる永続保存は導入しない。
- DBには写真の保存先識別子と、所有者・履歴書との対応を記録する。写真を公開URLで無条件に配信しない。
- 認証付き取得、または本人確認後に発行する短時間有効なURLを使用する。具体的な転送方法は設計時に確定する。
- 差し替え時は、新しい写真の保存と対応更新が成功する前に、旧写真を失わないようにする。
- DBとStorageの更新は一括で成功するとは限らないため、途中失敗を扱い、削除・後処理を再試行できるようにする。
- 初期版では、履歴書に紐付く写真を1枚管理する。独立した写真ライブラリは作らない。

### 保存と画面の状態

- 明示的な保存を基本とし、保存中・成功・失敗・未保存状態を区別する。
- 未保存状態で画面を離れる際に注意を表示する。
- ログアウト・アカウント切り替え時は、表示中の書類と写真をクリアし、別利用者の画面へ残さない。
- 写真の取得・表示が完了していない状態で、写真を含むPDFを誤って出力しないようにする。
- 書類内容、写真、トークン、秘密のキーをログ・公開資料へ出力しない。
- 初期版の削除対象は書類と対応写真。認証アカウントの退会機能やバックアップからの即時消去を保証する仕様は含めない。

## 6. 技術構成

| 担当 | 採用技術 | 役割 |
|---|---|---|
| 開発言語 | TypeScript | 画面とAPIの実装 |
| フロントエンド | React・Vite | 入力・編集・プレビューを行うSPAとビルド |
| 画面遷移 | React Router | ブラウザ側の画面遷移。SSR用のFramework Modeは導入しない |
| 自作API | Hono | 認証検証、入力検証、認可、書類CRUD |
| 画面公開 | Cloudflare Workers Static Assets | ビルドした画面ファイルの配信 |
| API公開 | Cloudflare Workers | Hono APIの実行 |
| 認証 | Supabase Auth | Googleログイン |
| DB | Supabase PostgreSQL・RLS | 書類保存と利用者別のアクセス制限 |
| 写真保存 | Supabase Storage | 非公開のファイル保存とアクセス制限 |
| PDF | ブラウザ印刷・印刷CSS | PDF保存と書類レイアウト |

文字データの経路は「React画面 → Hono API → PostgreSQL」とする。写真転送の詳細は設計文書で定める。Web画面の実装に依存しないHTTP APIを維持し、将来のAndroidからの利用を可能にする。

フォーム・入力検証・テスト用ライブラリ、APIの詳細、DBスキーマ、環境変数は実装設計で決定する。秘密値は文書やリポジトリへ記載しない。

## 7. 初期版の制限・対象外

書類作成・保存・PDF出力までの利用経路を優先し、初期版の範囲を以下へ絞る。認証・認可・入力検証は必須範囲に含める。

| 対象 | 初期版の方針 |
|---|---|
| 書類数 | 利用者ごとに履歴書1件・職務経歴書1件 |
| テンプレート | 各書類1種類 |
| PDFページ数 | 内容に応じて複数ページ可。「書類1件」は「PDF1ページ」の意味ではない |
| 保存 | 明示的な保存。自動保存・編集履歴は対象外 |
| 写真 | 履歴書用1枚。クラウド保存。高度なトリミング・写真履歴は対象外 |
| PDF生成 | ブラウザ印刷。サーバーPDF生成は対象外 |
| 公開・共有 | 他人への書類共有リンクは対象外 |
| 描画方式 | SPA。SSRは対象外、SSGは初期版に導入しない |
| 対応アプリ | Web版。Androidアプリは対象外 |
| 問い合わせ・紹介 | How to、About、Contact、アプリ更新履歴の専用ページは将来候補 |

## 8. 検証・完成判定

### 必須の確認

- [ ] F01〜F14の受け入れ条件を満たす。
- [ ] 公開環境でGoogleログインから入力・保存・再取得・プレビュー・PDFまで一通り操作できる。
- [ ] 別端末で、同じアカウントの書類と写真を取得できる。
- [ ] 未認証と別利用者による書類・写真のアクセスを拒否する。画面の非表示だけでなくAPI・保存先側も確認する。
- [ ] 不正な入力・画像、認証切れ、通信失敗、写真の差し替え・削除の途中失敗を扱える。
- [ ] 再ログイン・アカウント切り替えで他利用者のデータが表示されない。
- [ ] 削除後の取得結果と、関連写真の削除を確認する。
- [ ] 日本語・長文・複数プロジェクト・写真を含むPDFを目視確認する。
- [ ] 小さい画面とキーボードで主要操作を確認する。
- [ ] Lint・型チェック・Build・重要テストがローカルとCIで成功する。
- [ ] READMEに起動手順、環境変数の名前、検証手順、デモURL、初期版の制限を記載する。
- [ ] 架空の情報でデモと検証を行い、秘密値や実在の個人情報をリポジトリへ含めない。

確認したブラウザ・端末・テストケース・結果・未解決事項は検証記録へ残す。現時点では対応確認済み環境を断定しない。

### 利用者への価値の確認

初期版を実際に使い、書式を直接調整せずに書類を作成・PDF保存できるか、入力や保存で迷う箇所があるかを確認する。利用者から得られた問題・改善要望を記録し、追加機能の優先度を見直す。未測定の利用実績や成果を記載しない。
